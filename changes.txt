loopdata change history
-----------------------

7.1 2026/09/03
--------------
- Week, month, year, rain-year and all-time sums, counts and averages no
  longer count today twice after a restart.  Loopdata seeds those spans
  from the daily summary table and then adds today's running totals on
  top, but today has a row in that table too, so from a restart on,
  month.rain.sum and its kin read today's contribution double and every
  span average leaned toward today's mean.  Minimums and maximums were
  unaffected.  The error lasted until the span rolled over -- and for the
  all-time span, which never does, until the next restart doubled it
  afresh.
- When weewxd stops, loopdata stops its writer thread before the process
  ends, so a stop that lands while a packet is being written does not
  leave a LoopData temp file behind in the directory the loop-data file is
  served from.  Packets still queued at that moment are discarded rather
  than written and shipped to nobody.  Should the thread not stop within
  twenty seconds -- a stalled rsync could hold it that long -- the stop
  goes ahead without it and says so in the log.  A driver restart, where
  weewxd rebuilds its engine in the same process, likewise no longer
  leaves the previous writer thread and its accumulators behind.
- Should the writer thread die -- its traceback has always been logged --
  loop packets are no longer queued to it for the rest of weewxd's life,
  which grew memory by one packet every loop interval while the loop-data
  file sat frozen.  The loss is logged once more, saying the file will not
  update again.
- [[RsyncSpec]] skip_if_older_than must be at least 1.  Zero used to mean
  never skip, undocumented, and a station that set it would rsync every
  packet however late -- the backlog the option exists to prevent.  A
  value below 1, and a blank one, are now ignored with a warning and the
  default of 3 is used.
- When weewxd starts, the day accumulator is seeded from the daily summary
  of the first loop packet's day rather than the wall clock's.  The two
  differ only when a start straddles midnight in the second or so between
  a packet being stamped and being processed -- exceedingly unlikely in
  practice -- but when they did, the day's min/max/sum carried the wrong
  day's history until the packet-time day rolled over.
- Internal: the two archive database connections loopdata opened -- one
  when the service starts, one when the first loop packet builds the
  accumulators -- are closed when they are finished with, rather than
  held open for the life of weewxd.
- Internal: the test suite closes the files it writes, so a run no longer
  prints a ResourceWarning for each one.

7.0.1 2026/08/31
----------------
- Nothing below edits a weewx.conf that already exists, and there is
  nothing to do by hand.  The one change that reaches a station without an
  edit is the expiration_time default, immediately below.
- The sample page's default expiration_time is 24 hours, where it was 4,
  matching the sibling extensions.  This reaches a station that has no
  live expiration_time in weewx.conf: a fresh install, where the option is
  written commented out.  A station whose weewx.conf carries
  expiration_time = 4 as a live setting -- every install made before the
  option was demoted -- goes on expiring after 4 hours until that line is
  edited or removed.
- A fresh install writes eight options into weewx.conf commented out,
  each showing the value that will apply: compress, log_success, timeout
  and skip_if_older_than in [[RsyncSpec]], and loop_data_file,
  expiration_time, googleAnalyticsId and analytics_host in the sample
  report's [Extras] (the last two as examples -- their default is to be
  absent).  weectl fills in absent keys and never rewrites one, so an
  option written live freezes that station on today's default for ever,
  while a commented one leaves loopdata's own value to answer, including
  a better one a later release brings.  What stays live is what loopdata
  cannot supply for itself: the switches (enable), the placeholders a
  user must replace (remote_server, remote_user, remote_dir,
  page_update_pwd), what weectl needs (HTML_ROOT, skin), the station's
  loop cadence, the file's directory and name, and the sample report's
  string formats -- which are on the report's stanza so that a
  station-wide [[Defaults]] cannot put a decimal on a wind dial that has
  no room for one.
- Fixed: deleting enable, compress or log_success from [[RsyncSpec]] --
  or deleting the whole section -- stopped LoopData at startup with
  "Unknown boolean specifier: 'None'".  Each now falls back to false,
  which is what the installer has always written.
- The installer's [[ScriptData]] example of how to declare fields no
  longer lands in weewx.conf indented as though it belonged to
  [StdReport].  ConfigObj attaches a comment block to the next key and
  writes it at that key's indent, and the block sat after the section's
  last option.
- Fixed: a kiosk URL whose ?pageUpdate= password contains a space, or any
  other character a browser percent-encodes, now matches.  The password
  was compared still encoded, so such a password never exempted the page
  and the display went dead after expiration_time hours.  The URL value is
  compared both as typed and percent-decoded, so a URL that worked before
  -- including a password that itself contains a percent-escape -- goes on
  working untouched.
- Fixed: a quote or a backslash in page_update_pwd, refresh_rate or
  expiration_time no longer kills the page outright, and a page_update_pwd
  containing an accent or any other non-ASCII character now matches.  All
  three were written into the javascript as hand-quoted literals: a quote
  ended the string early, which is a parse error that stops the whole
  script -- no polling, no gauges -- and a non-ASCII password was rendered
  as a character reference, which could never equal what the URL supplied.
  All three are emitted with json.dumps now, as the page's translated
  strings already were, so a mistyped number falls back to its default
  instead of taking the page down.
- Fixed: blanking page_update_pwd no longer leaves every visitor's page
  polling for ever, and no URL exempts a page whose password is blank.
  An empty value used to be read as a password, so the empty ?pageUpdate=
  every visitor has matched it; it then fell back to a fixed word that is
  in the shipped source for anyone to read.  Now there is no password at
  all, which nothing in a URL can equal.  (An [Extras] option written
  empty is present, so the test for one fired on it.)
- expiration_time = 0 now means the page never expires, which is what a
  zero timeout ought to mean and what it never did: it expired the page
  before the first packet arrived, since ConfigObj yields strings and a
  '0' passed the template's test for a value.  It is the kiosk exemption
  without the ?pageUpdate= URL.
- Fixed: refresh_rate = 0 no longer polls as fast as the browser can; a
  page that never polls is a dead page, so zero means the default there.
  A negative, or a setting that is not a number, means the default for
  both -- rather than emitting javascript that stopped the whole script,
  and, for a negative expiration_time, rather than quietly never expiring.
- Fixed: a large expiration_time no longer expires the page at once.  Past
  2147483647 milliseconds (~596 hours) the delay overflows the browser's
  int32 timer and fires immediately, so an expiration_time of 1000, reached
  for as "effectively never", did the opposite.  It is clamped to that
  ceiling now, and zero is how you say never.
- Fixed: once the page has expired, the CLICK-ME prompt is written once
  rather than rewritten every couple of seconds for as long as the tab is
  open.  The test meant to prevent that compared the element itself
  against the string.
- Fixed: a page adapted without the sample skin's status elements no
  longer throws on every poll.  Each of the five places that writes the
  LIVE indicator or the timestamp -- including the OFFLINE, NO DATA and
  BAD DATA branches -- now goes through one guarded writer, and the gauges
  are drawn before the labels rather than after, so a missing label cannot
  stop the drawing.
- Fixed: a page adapted without the windrose legend's element no longer
  takes the eleven dials down with it.  The lookup is guarded, and the
  legend's cache key is now set only once the legend is built, which is
  what made the symptom intermittent.
- Fixed: a report that declares gauge fields but not the clock group now
  says BAD DATA -- check loop_data_file instead of reading "NaNs ago" and
  "Invalid Date" for ever.  The gauges still draw.
- Fixed: the sample page's windrose colours stretch to however many speed
  bands are configured.  The six shades were indexed one per band, so a
  seventh band wrapped around and painted the windiest band in the calmest
  band's colour -- in the rose and in its legend alike, so the page did not
  even look wrong.  They are stops on a curve now, sampled for the band
  count in use; six bands, which is what the default edges and the shipped
  sample configuration both produce, get exactly the six shades they
  always did.
- A README correction: the list of [LoopData] options had every rsync
  option, plus the loop frequency, sitting under the heading that marks the
  three deprecated ones -- so options a fresh install does write, and the
  block just above it shows being written, read as deprecated.  The
  deprecated three (target_report, fields and the [LoopData] spelling of
  windrose_bands) are together at the end of the list now, under that
  heading and nothing else.
- Fixed: the sample page's data age is measured against the web server's
  clock instead of the browser's, so a viewer whose device has the wrong
  time no longer sees a false age -- or, since the page reads LIVE only
  while the packet is younger than three times refresh_rate (six seconds by
  default), never sees LIVE at all over a perfectly healthy feed.  The age
  now comes from the Date header of the response that carried the record,
  plus any Age a proxy reports, and never reads the viewer's clock while
  that header is there.  A monotonic floor -- how long since the data last
  changed -- catches a cached copy whose header reads younger than its
  body.  Where no Date header reaches the page at all the viewer's clock is
  still the only measure available and is used, since otherwise a feed that
  had already stopped before the page loaded would read LIVE.
- Fixed: running weectl report run no longer drops a zero-byte LoopData
  file into the directory the loop-data file is written to -- which is
  inside the web-served report tree by default, and got one more on every
  run.  LoopData reserves a unique name at startup to write each packet to
  before renaming it onto loop-data.txt, and was leaving the empty file
  itself behind; only the name was wanted.  weewxd never left one, which is
  why this went unseen: the file is renamed away by every packet, and the
  cleanup that existed ran on the loop-processor thread, which weectl
  report run never starts even though report_services builds the service.
- The windrose manual page gains a picture of one: the sample skin's rose on
  a real morning, with the default bands, captioned so that the calm centre
  and the two-lobed shape illustrate the advice on choosing edges that
  follows it.
- Manual corrections: the windrose page's advice on the top band edge said
  the darkest color flags the strongest wind.  It is the other way round on
  the sample page, whose ramp runs dim for calm to bright for windy; some
  other windrose tools do run dark for fast, which is where the sentence
  came from.  The troubleshooting page's BAD DATA row gave only one of the
  three things that show it -- a body that is not json -- and not the two
  that name a report: no entry for this report at all, or an entry with no
  current.dateTime.raw in it.
- Fixed: a gauge whose cell is hidden because the station has no such
  sensor is re-sized when the sensor reappears.  A hidden element measures
  zero, so its canvas was built at a fallback size, and only the windrose
  was ever checked for that drift.
- Internal: three guard tests on the installer stanza -- the commented
  options pinned as a complete set with their values, each value checked
  against the fallback that governs when the key is absent, and comment
  placement checked through weecfg's own merge, counted so that a block
  dropped outright (which happens silently when it attaches to a section
  weewx.conf already has) fails.

7.0 2026/08/26
--------------
- ACTION REQUIRED, 1 of 3 -- WeeWX 4.6 or later: this release requires WeeWX
  4.6 or later, where 6.x required 4.0.  Both the installer and the
  service refuse to run on anything older.  4.6 is where WeeWX made its
  skin-dictionary builder a module-level function, which is how loopdata
  assembles each report's units, formats and language, and it is also
  where $gettext arrived, which the sample skin has needed since 6.4.
- ACTION REQUIRED, 2 of 3 -- FINISH THE MIGRATION by running user.loopdata
  as a command (the manual's Declaring fields page gives the command line
  for each way of installing WeeWX).  The fields line does
  not remove itself, and an upgraded station should remove it once every
  extension whose pages read the loop-data file declares its own fields.
  The command reports which report now covers each entry on the line and
  which are covered by nobody -- almost always cruft, entries a page asked
  for years ago and no longer reads -- and changes nothing until every
  entry is accounted for and it is run with --apply, which backs up
  weewx.conf, deletes [[Include]] and [[Formatting]], and moves
  [LoopData] windrose_bands onto the stanza of the report whose rose it
  bands (see the windrose_bands bullet below).  A relative loop_data_dir
  is pinned to the directory the file is in today first, since it was
  measured from target_report and that is going -- no page finds its URL
  gone.  It also runs with the fields line already deleted, to remove
  what is left.  The startup warning names the command.
- ACTION REQUIRED, 3 of 3 -- a live page of your own that reads
  loop-data.txt: declare its fields under its report and have the page read
  that report's entry, before the fields line goes.  Nothing is required
  for the sample page, weewx-celestial or weewx-weatherboard: upgrade each
  and it declares its own fields, and until then they keep working through
  the fields line exactly as before.
- Reports declare the fields they need.  A skin's skin.conf carries a
  [LoopData] [[fields]] section of named groups (see
  skins/LoopData/skin.conf), and every enabled report whose skin declares
  fields is its own target: its fields are rendered with its own
  formatter, converter, [Texts], [Almanac] names, $station and
  [Units] [Trend] time_delta, and written into loop-data.txt under the
  REPORT's name (the [StdReport] section name -- one skin can be listed
  under two reports, in two unit systems, and each gets its own values).
  A report can add to or override its skin's groups from weewx.conf
  ([StdReport] [[MyReport]] [[[LoopData]]] [[[[fields]]]]), which is how
  an extension declares fields that depend on your configuration.
  Accumulation is shared: one set of accumulators feeds every report.  The
  two report settings that reach the accumulators -- the trend window and
  the windrose band edges -- select an accumulator by value, so reports
  that agree share one and a report that differs gets its own.
- A fields line entry that any report declares and renders identically is
  rendered ONCE, in that report's entry, and copied flat, so a station
  still carrying the line pays almost nothing for it.  Two reports count
  as rendering identically when their units, formats, labels, texts,
  almanac names, trend window and windrose bands all match, which on a
  station whose reports inherit [StdReport] [[Defaults]] is every report.
  Only fields nothing declares, or that no matching report declares, are
  rendered for the line itself.
- windrose_bands is a report option.  On a report's stanza in [StdReport]
  it is in that report's windSpeed unit; under [StdReport] [[Defaults]] it
  applies to every report, in the Defaults' unit, converted to each
  report's and rounded to one decimal; a skin.conf may carry one too.
  The pre-7.0 [LoopData] windrose_bands is deprecated.  It bands
  target_report's rose and no other -- which is the one rose it banded
  before 7.0, the one in the flat file -- so that report keeps its bands
  and every other report takes the WRPLOT defaults until someone chooses
  otherwise.  Finishing the migration moves the value to that report's
  stanza, in the unit it is already written in, or simply drops it when
  that report already gets its bands from somewhere nearer.
- The [LoopData] [[Include]] fields line and [[Formatting]] target_report
  are deprecated, together with the flat top-level keys they produce.
  All three still work exactly as before on an upgraded station, so an
  existing page keeps reading what it always read, and the per-report
  entries appear in the same file beside them.  A fresh install writes
  neither.  weewxd logs a warning at startup while the line is present;
  do not edit it by hand -- an extension declares its own fields when
  installed, and a later loopdata release removes the line once every
  extension that used it declares its fields.  A live page of your own
  should declare its fields under its report (see the manual's Declaring
  fields page) before that happens.
- target_report keeps one job while it exists: a relative loop_data_dir
  is relative to its directory, LoopDataReport when target_report is not
  set.  So keep the [[LoopDataReport]] section -- enable = false turns
  the page off, and the installer puts a deleted section back.  A
  target_report kept after the fields line is gone is warned about at
  startup: set loop_data_dir to an absolute path before the release that
  removes it, or the file moves.
- A FRESH install writes no fields line, and weewx-celestial 8.4's
  installer only adds to a line that already exists, so a fresh station
  needs a weewx-celestial newer than 8.4 for the Celestial page to have
  live values.  Upgraded stations keep their line and are unaffected.
- One report's fields failing to render no longer stops the file.  Every
  enabled report's declaration is rendered on every packet now, including
  skins this station's operator never wrote; a failure drops that
  report's entry, logs once and leaves every other report's values
  written, where before it would have ended the loop-data thread and
  frozen the file while weewxd carried on.
- A report for consumers that are not reports.  A script, an SNMP
  extension or a monitoring check has no skin to declare fields in, and
  parking them on a page's report means an upgrade overwrites them.  The
  installer now writes a disabled [StdReport] [[ScriptData]] stanza and
  ships skins/ScriptData, a skin that generates nothing: enable the
  report, declare your fields under its stanza in weewx.conf, and they
  arrive in the loop-data file under "ScriptData".  The manual's
  Declaring fields page has the details.
- A field none of the parsers accept is now logged as a warning, naming
  the report that declared it.  It was dropped silently.
- A single-field fields value (no comma, which ConfigObj hands back as a
  string) is read as one field.  It was iterated character by character.
- The sample skin declares its fields in its skin.conf, grouped by gauge,
  and its page reads its own report's entries.  The installer no longer
  writes a fields line or a target_report.
- Internal: Configuration is split into the shared half and a
  ReportContext per report; generate_loopdata_dictionary is split into
  accumulate_packet and render_report; the almanac and station
  evaluators are per report (their caches hold rendered values).

6.11.3 2026/08/24
-----------------
- The sample page no longer loads Google Analytics when no analytics id
  is configured.  analytics.inc tested whether googleAnalyticsId was
  PRESENT, not whether it had a value -- and the installer writes it
  present but empty.  Every install that took the default therefore
  fetched https://www.googletagmanager.com/gtag/js?id= on every page
  view, with an empty id: a third-party request nobody asked for, on a
  page whose owner had never configured analytics.  The companion option
  failed the same way in the other direction: with analytics_host present
  but empty the page compared its hostname against "", which is never
  true, so a user who did set an id and left the host alone got the
  script loaded and not one event reported.  Both now test the value.
  Empty means off for googleAnalyticsId, and means report from wherever
  the page is served for analytics_host -- which is what both options
  always claimed.  Existing installs pick this up on their next report
  cycle; no configuration change is needed.  The manual documents both
  options for the first time -- they had never appeared in docs/ or the
  README, and the test that is supposed to catch that read only
  skin.conf, where both sit commented out and so were invisible to it.
  It now also reads the [[[Extras]]] the installer writes.
- Blanking refresh_rate or expiration_time in weewx.conf no longer kills
  the sample page.  realtime_updater.inc tested those two for PRESENCE and
  emitted the value straight into a javascript assignment, so an empty one
  rendered "refresh_rate = ;" -- a parse error that took down the whole
  script block, and with it the polling, the gauges and the translated
  strings, not merely the one setting.  Both now test the value and fall
  back to their defaults, as a missing option always did.  Same fix as the
  analytics options above; page_update_pwd was never affected, its value
  being quoted.
- The [LoopData] stanza a fresh install writes into weewx.conf arrives
  commented.  It had always landed as bare key = value lines with
  nothing to say what any of them did, which left the manual as the only
  way to find out what, say, [[LoopFrequency]] seconds was for -- and
  that is the option whose wrong value silently scales every windrun and
  every windrose distance.  Now each section and each option carries a
  line or two explaining itself, the three placeholders in
  [[RsyncSpec]] say they are placeholders, and the fields line says what
  a field is and where the full grammar lives.  The cause was that the
  installer built its stanza as a Python dict: weectl merges it with
  weeutil.config.conditional_merge, which copies a key's comments across
  only if the source has any, and a dict has none.  The stanza is now a
  ConfigObj, which does.  Existing installs are untouched -- the merge
  fills in absent keys only, and every value written is unchanged, so
  this matters only on a fresh install.
- The manual no longer says the sample panel calls its data stale after
  expiration_time seconds.  Both halves were wrong: expiration_time is in
  hours, and it is the poll-forever timeout, not a staleness test.  The
  panel reads LIVE while the packet is no older than three times the
  skin's refresh_rate -- six seconds by default -- and shows the age
  instead once it is older.  The passage's point is unchanged; only its
  numbers were.
- Internal: three tests pin the new stanza -- that every section and
  option in it is commented, that the comments survive a merge driven
  through weecfg's own ExtensionEngine._inject_config (which is where the
  stanza is copied, and the copy is what decides whether comments survive
  at all), and the values a fresh install writes.
- Internal: install.py builds its ConfigObj inside the installer rather
  than at import time, so loader()'s "requires WeeWX 4" message is
  reachable again.  A module-level import of weeutil.config ran before
  that check and could not survive a WeeWX 3 install -- the module is
  absent before 3.9, and 3.9's copy has no config_from_str -- so the
  user got a raw traceback instead of the message.

6.11.2 2026/08/24
-----------------
- The manual says where the loop-data file should live.  The default --
  inside your reports tree, in the target report's own directory --
  works, and is what most stations keep.  Two things are worth knowing
  all the same: the file is rewritten on every loop packet, which a
  station running from an SD card may rather have land in RAM, and the
  report sync copies that tree every report cycle, which buys nothing
  when the pages are served from the same machine.  A memory filesystem outside the web root answers both, for
  anyone comfortable editing a web server configuration: the new
  section carries the /dev/shm and fstab recipes, the Apache and nginx
  aliases (with the no-store header a live page wants), the URL the
  reading page then needs, and the case none of it helps: where the
  report sync is the only way to reach the machine serving the pages,
  as it is when publishing by FTP, the file crosses only at report
  cadence and cannot feed a live page at all.  That wants loopdata's
  own rsync, or pages served from the machine weewx runs on.
- Upgrading gains a 6.11.2 line.
- The manual no longer calls the loop frequency crucial without saying
  what it costs.  It is crucial; now it says why.  Only live packets are
  weighted with this value: every period that outlives weewxd's startup
  -- hour, day, week, month, year, rainyear, alltime and the rolling
  windows -- is seeded from what is already in the database, at the
  weights the archive gives it.  So a wrong value skews the ratio
  between the seeded part of a period and the live part rather than
  cancelling out of the average, and the manual works an example
  through: a station emitting every two seconds but configured for four
  counts its evening twice over, and day.outTemp.avg reads 16.0 where
  it should read 17.5.  The skew is bounded by the period's own length
  -- it clears when the period rolls or the seeded records age out of a
  rolling window -- and minima and maxima never use the weight at all.
  windrun and windrose are the ones that do not recover: both are wind
  speed times that interval, so they scale straight with the error and
  no roll-over cleans them, and day.windrose.banded is what the sample
  panel draws.  Two seconds is also no longer stated as a fact about
  hardware in general: it is what a Davis Vantage emits, with nothing
  to set on the station side, while a driver you poll on a schedule
  hands you the number directly.
- The manual carries the new section everywhere a reader chooses the
  value, not just where the option is defined: Installation and Build a
  live page both point at it, and Troubleshooting's NO DATA (HTTP 404)
  row no longer reads as a warning against the very arrangement the
  manual now recommends -- keeping the file outside the web root is
  fine, it just has to be served and named.
- The fstab recipe in that section says to create the mount point and
  give it to the user weewxd runs as.  A root-owned mode=0755 tmpfs is
  not writable by a weewxd running as anyone else, and the failure is
  unhelpful: the directory exists so makedirs succeeds, and it is the
  temp file opened next that raises PermissionError, during service
  init, so weewxd does not start.  /dev/shm needs neither step.
- Internal: the absolute-manual-URL audit checks a link's #fragment
  against the target page's headings again.  It had been made to strip
  the fragment so an anchored link would pass the .html check, which
  left the repo's first anchored absolute link unverified -- rename the
  section and the link would have died silently.
- The sample skin's shipped loop_data_file is the value every install
  actually runs: loop-data.txt, the file beside the page, matching the
  default loop_data_dir = . .  skin.conf shipped ../loop-data.txt --
  dead text, since weewx.conf's own entry overrides it -- and the
  manual documented that value and explained it wrongly.  No install
  changes behaviour; a reader of either file is no longer misled.

6.10 2026/08/13
---------------
- Almanac fields work again on WeeWX earlier than 5.3.  WeeWX 5.3
  renamed the Almanac constructor's language argument: it now takes
  texts (the target report's whole [Almanac] section -- moon phases,
  body names, constellation names), where earlier versions took
  moon_phases, the eight phase names alone.  Since almanac fields
  shipped in 5.0 loopdata has passed texts unconditionally, which is a
  TypeError on WeeWX 4.x through 5.2: at the first loop packet the
  LoopData thread logged a traceback and stopped, and loop-data.txt was
  never written again -- weewxd itself kept running, so the only signs
  were the traceback in the log and a page frozen at its last values.

6.9 2026/08/08
--------------
- A next_* almanac field now expires the moment its event's own instant
  passes, instead of being kept until midnight: a "next" value whose
  instant is behind us no longer is what the field name promises.
  Fields naming the same event -- say a satellite pass's rise, set and
  maximum altitude -- are computed together and expire together, at the
  latest time-typed value among them (for a pass, the set time), so an
  in-progress pass keeps serving until it ends and the very next packet
  carries the following pass, every field switching at once.
  Recomputes stay rare by construction, since each one returns the next
  occurrence, re-arming the cache: next_full_moon recomputes once per
  lunar month, a satellite's next_pass once per pass.  A group with no
  time-typed field cannot see its event end and keeps the once-per-day
  refresh -- include a pass time field to get event-time expiry.
  previous_* fields are unchanged (their instant is always in the past;
  they refresh once per local day).  The stale window has been there
  since almanac fields shipped in 5.0 -- almanac.next_full_moon serves
  the old event from the instant it passes until midnight -- but it
  took developing weewx-celestial 8.0's "Next pass overhead" panel
  against this code to make it glaring: driven by the old caching, the
  panel showed a morning pass as "just set" until the day's end.  Fixed
  before either shipped.
- A day- or event-tier almanac field that evaluates to no data is no
  longer cached until the next local day: every packet retries, so the
  field picks up its value the moment the almanac has data.  Seen live
  with weewx-skyfield satellites: a newly added satellite's rise,
  set and pass fields honestly read N/A until its orbital elements
  downloaded, but before this fix they kept reading N/A until midnight
  even though the elements arrived moments after startup.
- Complete Italian, Norwegian (Bokmål) and Swedish translations ship

  native-speaker review -- corrections welcome): lang/it.conf,

6.1 Release 2026/07/24
----------------------
Fixed: a dead or hanging rsync remote could stall loop processing for
minutes per attempt despite timeout = 1.  That setting only reached rsync's
--timeout, which bounds rsync protocol I/O, not the phases ssh owns: a
black-holed TCP connect, a stalled handshake, or an auth prompt could each
block the LoopProcessor thread far longer (the file kept its full age
backlog: written minutes after the packet inside it was stamped, dial pages
frozen).  LoopData now folds ssh-side bounds into the rsync transport --
ConnectTimeout=<timeout>, ServerAliveInterval=<timeout>,
ServerAliveCountMax=2 and BatchMode=yes -- each applied only if your own
ssh_options doesn't set that keyword, so anything you set wins.  Previously
the ConnectTimeout=1 default lived in the ssh_options default value itself,
so setting ssh_options at all (a key file, a port) silently discarded it.
Setting timeout = 0 disables the time bounds (BatchMode is still applied:
an interactive prompt can never be answered under weewxd).

6.0 Release 2026/07/22
----------------------
Action required if you publish the sample report: upgrading replaces the
sample skin's page with the new instrument panel (below) but keeps your
existing [LoopData] fields line, and the panel reads fields the old default
never included (.raw geometry, unit.label scales, day.windrose.*) -- so with
an old fields line the new page serves half-dead: text readouts but no
needles, min-max bands or windrose.  Replace the fields line under
[LoopData] [[Include]] with the one in the README's sample configuration
(exactly the fields the panel reads; append any fields other pages of yours
use) and restart weewxd.  Fresh installs get it by default.

Removed (action required if you used them): the experimental windrun_<dir>
observation types (windrun_N ... windrun_NNW) are gone, replaced by the
first-class windrose observation below.  Fields naming them are now ignored.
To migrate: day.windrun_N.sum is element 0 of day.windrose.sum,
day.windrun_NNE.sum element 1, and so on clockwise through NNW (element 15).
The windrun_<dir> types were always documented as experimental and likely to
change; this is that change.

New: windrose.  A NOAA-style windrose for any period except current and trend
-- including week, month, year, rainyear and alltime, which windrun_<dir>
never supported.  Per period, loopdata accumulates 16 compass bins x N speed
bands, each cell tracking both seconds and distance, plus a directionless
calm total (wind below the calm threshold, or no wind direction).  Four
aggregates project the matrix into json: .sum (16 distances -- windrun
parity, unit-convertible, .formatted-able; sub-calm-threshold wind counts as
calm time, not distance), .time (16 durations in seconds),
.banded (the 16xN seconds matrix -- the NOAA rose), .calm (scalar seconds).
Arrays emit json numbers; .round(n) applies per element.  A windrose.bands
key (band edges, target report windSpeed units) is emitted automatically so
page legends never hardcode the bands, and unit.label.windrose gives the
distance label.  Band edges default to the classic WRPLOT/NOAA bands (0.5,
2.1, 3.6, 5.7, 8.8, 11.1 m/s, shown in report units); override with
[LoopData] windrose_bands (ascending edges in the target report's windSpeed
unit; the first edge is the calm threshold).  Span periods seed at startup
with a single SQL aggregate per period, so even alltime.windrose starts fully
primed.  The sample LoopData skin now draws a live canvas windrose.

Fixed (via the windrose rework): after a weewxd restart, hour-period and
continuous-period (1m-1440m/1h-24h) windrun_<dir> buckets started EMPTY and
silently filled as packets arrived -- archive-replay priming never carried
the bucketed values.  windrose accumulators seed every period from the
archive at startup.

Changed (check your pages): time-of-event fields (maxtime, mintime,
firsttime, lasttime) now format with the field's period as the time context,
exactly as WeeWX report tags do -- the target report's [Units][TimeFormats]
entry for that period applies.  With the standard TimeFormats, day.*
times now render as 12:00:00 instead of 07/01/20 12:00:00, hour.* times as
12:00, week.* times as 12:00:00 (Wednesday); month/year/rainyear are
unchanged, and alltime uses the year format (the context WeeWX binds for the
$alltime tag), also unchanged with the standard TimeFormats.  Continuous
periods (1m-1440m, 1h-24h) keep the 'current' format.  In addition, .formatted on a time-of-event field now
yields the same context-formatted time (times carry no label) instead of an
unusable raw-number rendering.  If your page relied on the old full
date-time rendering for day/hour/week times, either adjust the page or set
that period's format in the target report's [Units][TimeFormats].

New: unit override in the fields grammar.  A field may now name an explicit
unit between the aggregation and the format spec
(period.obstype[.agg_type][.unit][.format_spec]), exactly as WeeWX report
tags allow (e.g., current.windSpeed.beaufort, day.outTemp.avg.degree_C.raw,
10m.windGust.max.knot.raw, trend.barometer.mbar.formatted).  Any unit WeeWX
knows for the observation's unit group is accepted, regardless of the target
report's configured units -- handy for gauges (e.g. Beaufort wind) that expect
a fixed unit.  The override is on value fields only; the unit.label prefix form
is unchanged (WeeWX parity: $unit.label is obstype-only).  A unit incompatible
with the observation's group causes the field to be omitted.

New: call-syntax format specs.  The formatting methods WeeWX report tags can
call are now format specs, with the same names, arguments and output:
format(format_string, None_string, add_label, localize), nolabel(format_string,
None_string), string(None_string) and long_form(format_string, None_string) --
e.g. day.outTemp.maxtime.format("%H:%M"), current.outTemp.format(add_label=False),
day.windGust.max.nolabel("%.0f"), day.sunshineDur.sum.long_form().  Arguments
must be literals; positional arguments bind exactly as the report tag's do.  A
bare spec name (day.rain.sum.string) is a zero-argument call, as Cheetah
renders it.  The unit override composes (day.outTemp.avg.degree_C.nolabel("%.2f")),
and the calls work on almanac fields too (almanac.sunrise.format("%H:%M")).
string(), or an explicit None_string argument, additionally makes a field with
missing data EMIT its None rendering (N/A or the None_string), overriding
loopdata's omit-missing-fields default -- handy for pages that want every key
present from the first packet.  NOTE: a call containing a comma must be quoted
in weewx.conf ('day.rain.sum.format("%.2f", add_label=False)') or ConfigObj
splits the entry at the comma.

New: round(n).  A field may round its value before rendering, exactly as
report tags allow -- day.outTemp.max.round(1).raw, or with a unit override,
day.barometer.max.mbar.round(1).raw.  Ordered between the unit override and
the format spec (period.obstype[.agg_type][.unit][.round(n)][.format_spec]);
composes with every format spec (round(2).format("%.3f") renders the rounded
value) and works on almanac fields (almanac.moon.az.round(1).raw).  Most
useful with .raw, to publish numbers with limited digits (29.93 instead of
29.927100000000002).

Fixed: the target report's options are now assembled by WeeWX's own
build_skin_dict when it exists (loopdata was looking it up under a stale name,
so it always fell back to its own assembly), and the fallback now disables
ConfigObj interpolation exactly as WeeWX does.  Without this, the %(hour)d-style
delta-time format strings misparse and long_form() cannot render.

New: the sample LoopData skin is a live instrument panel.  A NOAA windrose
plus eleven canvas gauges in three rows of four -- temperature, dew point,
feels-like and humidity dials wearing today's min-max as a band, a wind
compass with a ghost needle at the 10-minute gust direction, a barometer
with the 3-hour trend drawn as an arc (chevron showing the direction of
travel), rain and rain-rate dials that rescale themselves on a big day,
UV, solar radiation and air quality (weewx-purple's pm2_5_aqi) -- in a few
hundred lines of dependency-free javascript to crib from, replacing the
old tables page.  The gauges scale with the window: the engine draws in a
240-unit coordinate system stretched to the css size, so geometry and
fonts grow together on a wide display (faces cap at 480px).  Gauges for
observations the station does not report
(UV/radiation/air quality without the sensor, feels-like without appTemp)
hide themselves and reappear if the field shows up.  The .raw fields drive
the geometry, report-formatted fields supply every readout, and unit.label
fields pick the dial scales, so the panel follows the target report's
units (metric or US) automatically.  Fresh installs get the fields line
the panel needs; upgrading installs keep their existing fields line -- see
the action-required item at the top of this release.

Docs: the README now opens with the point -- report tags updated on every
loop packet -- and a four-step example (report tags, the same tags on the
fields line, the loop-data.txt they produce, and the javascript that makes
the page live).

Internal: the per-aggregate dispatch in add_period_obstype was refactored into
per-stats-kind extractor tables (SCALAR_AGGS/VEC_AGGS/FIRSTLAST_AGGS), and the
grammar's set of valid aggregate types is now derived from those tables, so
the parser and the dispatch can never drift apart.  No behavior change.

Internal: the format-spec render block that was repeated in the current,
period and trend paths is now a single renderer dispatching through a
FORMAT_SPECS table, and the grammar's set of valid format specs (and the
almanac grammar's) is derived from that table, just like the aggregate
types.  No behavior change.

Internal: the test suite moved from bin/user/tests to a top-level tests
directory.  No change to the installed extension.
